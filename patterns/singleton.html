Singleton

يضمن إن الـclass ليها نسخة واحدة بس في النظام، ويوفّر نقطة وصول عامة ليها. وهو أكتر pattern مختلف عليه — لازم تعرف ليه.

افتكرها

Singleton = نسخة واحدة بس. لكنه أكتر pattern بيتساء استخدامه — وكتير بيعتبروه anti-pattern.

1الشكل الكلاسيكي

class Config
{
    private static ?self $instance = null;
    private array $values = [];

    private function __construct()
    {
        $this->values = require 'config.php';
    }

    public static function getInstance(): self
    {
        if (self::$instance === null) {
            self::$instance = new self();
        }

        return self::$instance;
    }

    private function __clone() {}
    public function __wakeup() { throw new Exception('Cannot unserialize'); }
}

// الاستخدام
Config::getInstance()->get('app.name');

العناصر الأساسية: private __construct (منع الـnew)، static instance، وgetInstance().

2ليه كتير بيعتبروه anti-pattern؟

أربع مشاكل حقيقية
  1. Global state مخفي — أي class بتنادي Config::getInstance() عندها dependency مخبّية مش ظاهرة في الـconstructor. ده بيكسر DI.
  2. Testing صعب — مش تقدر تحقن fake. والـstate بيفضل موجود بين الـtests فتلاقي test بيأثر على اللي بعده.
  3. بيكسر SRP — الـclass بقت مسؤولة عن شغلها وعن التحكم في دورة حياتها.
  4. Concurrency — في بيئات multi-threaded محتاج locking، وفي PHP-FPM كل request له نسخته أصلًا (فالـ«نسخة واحدة» وهم).
// المشكلة في الـtest
public function test_something()
{
    Config::getInstance()->set('mode', 'test');
    // ...
}

public function test_another()
{
    // الـinstance لسه شايلة 'test' من الـtest اللي فات
    // ومفيش طريقة نضيفة تصفّرها
}

3البديل الأفضل

✕ Singleton
class OrderService
{
    public function process(): void
    {
        $config = Config::getInstance();
        // dependency مخفية
    }
}
✓ DI Container بـsingleton lifetime
class OrderService
{
    public function __construct(
        private Config $config
    ) {}
    // dependency معلنة وقابلة للاستبدال
}
الفرق المهم

في Laravel، $this->app->singleton(Config::class, ...) بيدّيك نسخة واحدة برضه — لكن:

  • الـclass نفسها عادية، من غير getInstance().
  • الـdependency معلنة في الـconstructor.
  • في الـtests تقدر تعمل bind لـfake بسطر واحد.

يعني كسبت «نسخة واحدة» من غير أي من عيوب الـSingleton. ده الشكل الصح دلوقتي.

4امتى Singleton مقبول؟

  • الـobject ملوش state بيتغيّر (stateless) — زي logger بسيط.
  • الـcontainer نفسه (لازم يكون فيه نقطة دخول واحدة).
  • كود قديم ومفيش container، والبديل هيبقى تمرير الـobject في 15 طبقة.

وحتى في الحالات دي، خلي getInstance() مستخدمة في نقطة التجميع بس (الـbootstrap)، مش منتشرة في كل الـbusiness logic.

5Interview

رأيك في Singleton؟

«الـSingleton بيضمن نسخة واحدة، لكن تكلفته إنه بيخبّي الـdependencies ويصعّب الـtesting لأني مقدرش أحقن بديل. في الأنظمة الحديثة بحقق نفس الهدف عن طريق الـDI container: بسجّل الـservice بـsingleton lifetime، فباخد نسخة واحدة، والـclass تفضل عادية والـdependency معلنة في الـconstructor. فبستخدم الـpattern نفسه نادرًا جدًا.»

الخلاصة

عارف الـpattern، وعارف ليه غالبًا مش بتستخدمه — دي أحسن إجابة في الإنترفيو.

افتكرها

Interpreter = حوّل قواعد اللغة الصغيرة لـclasses، وركّبهم عشان تفسّر التعبير.

1المشكلة

عندك نظام صلاحيات، والقواعد بتتكتب كنصوص:

"role = admin"
"role = editor AND department = sales"
"(role = admin OR role = owner) AND active = true"

الحل الساذج: تعمل parser بـifات وregex — وأول ما تضيف NOT أو أقواس متداخلة، الكود بيتحوّل لكابوس.

2الحل

interface Expression
{
    public function interpret(Context $context): bool;
}

// Terminal expressions — الأوراق
class EqualsExpression implements Expression
{
    public function __construct(
        private string $key,
        private string $value,
    ) {}

    public function interpret(Context $context): bool
    {
        return $context->get($this->key) === $this->value;
    }
}

// Non-terminal expressions — التركيب
class AndExpression implements Expression
{
    public function __construct(
        private Expression $left,
        private Expression $right,
    ) {}

    public function interpret(Context $context): bool
    {
        return $this->left->interpret($context)
            && $this->right->interpret($context);
    }
}

class OrExpression implements Expression
{
    public function __construct(
        private Expression $left,
        private Expression $right,
    ) {}

    public function interpret(Context $context): bool
    {
        return $this->left->interpret($context)
            || $this->right->interpret($context);
    }
}

class NotExpression implements Expression
{
    public function __construct(private Expression $inner) {}

    public function interpret(Context $context): bool
    {
        return ! $this->inner->interpret($context);
    }
}

التركيب

// (role = admin OR role = owner) AND active = true
$rule = new AndExpression(
    new OrExpression(
        new EqualsExpression('role', 'admin'),
        new EqualsExpression('role', 'owner')
    ),
    new EqualsExpression('active', 'true')
);

$rule->interpret($context);   // true / false
AND / \ OR equals(active, true) / \ equals(role, equals(role, admin) owner)

لاحظ إن الشكل ده شجرة — وعشان كده الـInterpreter قريب جدًا من الـComposite.

4امتى ما تستخدموش

أقل patterns استخدامًا عمليًا
  • لو اللغة معقدة (أكتر من 10-15 قاعدة)، الـpattern بيتحوّل لـclasses كتير جدًا — استخدم parser generator حقيقي.
  • لو اللغة موجودة بالفعل (SQL، JSON، regex)، استخدم parser جاهز.
  • الأداء ضعيف — كل تقييم بيمشي على الشجرة من جديد.

مناسب بس لما: اللغة صغيرة جدًا وثابتة، والقواعد بتتكرر، وعايز المستخدمين يكتبوا التعبيرات دي بنفسهم.

5في العالم الحقيقي

  • Specification Pattern — نفس الفكرة بالظبط لقواعد الـdomain: $spec->and($other)->isSatisfiedBy($order).
  • Feature flags / rule engines — قواعد استهداف بيكتبها فريق المنتج.
  • Query builders — تركيب شروط WHERE بشكل شجري.
  • Validation rules — required|email|unique:users في Laravel.

6Interview

Why Interpreter?

«لما يكون عندي لغة صغيرة أو مجموعة قواعد بتتكرر، بمثّل كل قاعدة كـclass، والتعبير المركّب بيبقى شجرة من الـclasses دي. أشهر شكل عملي ليه هو الـSpecification Pattern في قواعد الـdomain. بس نادرًا بستخدمه لأنه بيتوسّع بسرعة، ولو اللغة كبرت بستخدم parser حقيقي.»

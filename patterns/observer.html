Observer

بنستخدمه لما حاجة تحصل أو تتغيّر، وفيه أجزاء أخرى مهتمة تعرف وتعمل رد فعل.

افتكرها

Observer = حاجة حصلت، وكذا جزء عايز يتفاعل معاها — من غير ما الـsource يعرف تفاصيل كل رد فعل.

1المشكلة

Order Created ↓ ┌─────┼──────────┬────────────┐ ↓ ↓ ↓ ↓ Email SMS Warehouse Statistics
class OrderService
{
    public function createOrder()
    {
        // create order
        // send email
        // send SMS
        // notify warehouse
        // update statistics
    }
}
المشكلة

الـOrderService بقى عارف كل الأشياء اللي بتحصل نتيجة إنشاء الـOrder. كل ما نضيف reaction جديدة، نضطر نعدّل الـservice — وهو أصلًا مسؤول عن إنشاء الطلب بس.

2الفكرة

بدل ما الـOrderService يعرف كل التفاصيل، نعلن إن الحدث حصل، والأجزاء المهتمة تتفاعل:

Order Created ↓ Observers ↓ ┌─────┼──────────┐ ↓ ↓ ↓ Email SMS Warehouse
interface OrderObserver
{
    public function handle(Order $order): void;
}

class OrderService
{
    private array $observers = [];

    public function subscribe(OrderObserver $observer): void
    {
        $this->observers[] = $observer;
    }

    public function createOrder(array $data): Order
    {
        $order = Order::create($data);

        foreach ($this->observers as $observer) {
            $observer->handle($order);
        }

        return $order;
    }
}

دلوقتي إضافة reaction جديدة = class جديدة + سطر تسجيل. الـcreateOrder ما اتلمسش.

الـObserver Pattern أوسع من الـdatabase والـEloquent. مش لازم يكون عندنا database أصلًا — الفكرة عن الإعلان والاستجابة، مش عن الـmodels.

5التكلفة الخفية

الـObserver بيخفي تدفق التنفيذ

أكبر عيب: لما تقرا createOrder()، مش هتعرف إيه اللي بيحصل بعدها. لازم تدوّر على كل الـlisteners المسجّلين.

  • الـdebugging بيبقى أصعب — الـstack trace مش بيحكي القصة كاملة.
  • ترتيب التنفيذ غالبًا غير مضمون.
  • لو listener رمى exception، إيه اللي يحصل للباقيين؟ لازم تقرر ده صراحةً.
  • ممكن تلاقي listener بيعمل حاجة أساسية للعملية — وده خطر، لأن العملية بقت معتمدة على حاجة مخفية.

القاعدة: استخدم Observer للـside effects (إشعارات، إحصائيات، logging)، مش للخطوات الأساسية اللي العملية ما تكملش من غيرها.

6Interview

What is the Observer Pattern?

«بستخدمه لما يحصل event معين، ويكون عندي أكتر من جزء في السيستم مهتم بالحدث ده. بدل ما الـobject الأساسي يعرف كل الأجزاء اللي لازم تتفاعل، بخليه يعلن إن الحدث حصل، والـobservers كل واحد يتصرف بطريقته. كده إضافة reaction جديدة ما تخلينيش أعدّل الـbusiness logic الأساسية.»

الخلاصة

لما حاجة تحصل أو تتغيّر، الأجزاء المهتمة تتبلّغ وتعمل رد فعل من غير ما الـsource يعرف تفاصيل كل رد فعل.

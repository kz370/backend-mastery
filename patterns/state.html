State

سلوك الـobject بيتغيّر حسب الـstate الحالية بتاعته — فبدل if/else متكررة، كل حالة تبقى object مسؤول عن سلوكه.

افتكرها

State = حالتي بتحدد سلوكي.

1المشكلة

عندنا Order بالحالات:

Pending → Pay · Cancel Paid → Ship Shipped → Deliver Delivered → Return Cancelled → No operations

كل State ليها عمليات مسموحة وممنوعة. والحل المباشر:

if ($order->status === 'pending') {
    // ...
} elseif ($order->status === 'paid') {
    // ...
} elseif ($order->status === 'shipped') {
    // ...
}
المشكلة التصميمية

نفس معرفة الـStates بتتكرر في pay() وcancel() وship() وdeliver().

  • لو قواعد الـState اتغيّرت، ممكن تضطر تعدّل أماكن كتير.
  • الـOrder بيبدأ يعرف تفاصيل سلوك كل State.
  • إضافة حالة جديدة (refunded) بتلمس كل الـmethods.

2الفكرة

OrderState ↓ PendingState · PaidState · ShippedState · DeliveredState · CancelledState Order ↓ Current State
interface OrderState
{
    public function pay(Order $order): void;
    public function cancel(Order $order): void;
    public function ship(Order $order): void;
    public function deliver(Order $order): void;
}

class PendingState implements OrderState
{
    public function pay(Order $order): void
    {
        $order->setState(new PaidState());
    }

    public function cancel(Order $order): void
    {
        $order->setState(new CancelledState());
    }

    public function ship(Order $order): void
    {
        throw new Exception('Pending order cannot be shipped.');
    }

    public function deliver(Order $order): void
    {
        throw new Exception('Pending order cannot be delivered.');
    }
}

class PaidState implements OrderState
{
    public function pay(Order $order): void
    {
        throw new Exception('Order is already paid.');
    }

    public function cancel(Order $order): void
    {
        $order->setState(new CancelledState());
    }

    public function ship(Order $order): void
    {
        $order->setState(new ShippedState());
    }

    public function deliver(Order $order): void
    {
        throw new Exception('Paid order cannot be delivered.');
    }
}

الـOrder نفسه بقى بسيط

class Order
{
    private OrderState $state;

    public function __construct()
    {
        $this->state = new PendingState();
    }

    public function pay(): void      { $this->state->pay($this); }
    public function cancel(): void   { $this->state->cancel($this); }
    public function ship(): void     { $this->state->ship($this); }
    public function deliver(): void  { $this->state->deliver($this); }

    public function setState(OrderState $state): void
    {
        $this->state = $state;
    }
}

الـFlow

new Order() → PendingState $order->pay() → PendingState::pay() → PaidState $order->ship() → PaidState::ship() → ShippedState $order->deliver() → ShippedState::deliver()→ DeliveredState
نقطة مهمة

مش لازم كل object يبدأ بـState اسمها Pending — دي قاعدة الـOrder في المثال ده. المهم إن الـobject عنده Current State، والـState الحالية بتحدد السلوك.

3المكسب الحقيقي

  • قواعد كل حالة مجمّعة في مكان واحد — عايز تعرف الـPaid بيسمح بإيه؟ افتح ملف واحد.
  • الانتقالات بقت معلنة في الكود بدل ما تكون ضمنية.
  • إضافة حالة جديدة = class جديدة، والـinterface بيجبرك تحدد سلوك كل العمليات فيها.
  • الـOrder نفسه بقى نضيف: بيفوّض بس.

4Strategy vs State

الفرق الجوهري: في الـState، الحالة نفسها بتقرر الحالة الجاية. ودي حاجة مالهاش وجود في الـStrategy.

5امتى ما تستخدموش

التكلفة

لو عندك شرط بسيط أو حالتين قليلة ومفيش سلوك معقد، الـif العادية ممكن تكون أوضح وأبسط. الـState بتستحق لما الـstate-dependent behavior يكبر ويتكرر في methods كتير، والـif/else الخاصة بالحالات تبدأ تشتت المسؤوليات.

كمان خد بالك: 5 حالات × 4 عمليات = 20 method لازم تتكتب. لو معظمهم بيرموا exception، فكّر هل الـState محتاجة أصلًا ولا جدول انتقالات (transition map) بسيط هيكفي.

6Interview

امتى تستخدم State بدل if/else؟

«لو سلوك الـobject بيتغيّر حسب الـstate، وبدأت قواعد كل state تتكرر في methods كتير، بفصل كل state في object مسؤول عن سلوكها. لو الشرط بسيط وموجود في مكان واحد، الـif ممكن يكون أفضل. والفرق عن الـStrategy إن هنا الحالة نفسها هي اللي بتقرر الحالة اللي بعدها.»

S — Single Responsibility Principle

كل class يكون مسؤول عن حاجة واحدة أساسية، ويكون عنده سبب واحد رئيسي للتغيير.

محتويات الصفحة
  1. مثال فيه مشكلة
  2. شكل أفضل
  3. إزاي أعرف؟
  4. الحدود الصح
افتكرها

السؤال الذهبي: لو اتطلب مني تغيير طريقة إرسال الإيميل، هل لازم ألمس كلاس الـUser؟

1مثال فيه مشكلة

class User
{
    public function saveToDatabase()
    {
        // save user
    }

    public function sendEmail()
    {
        // send email
    }

    public function generateReport()
    {
        // generate report
    }
}

الـUser هنا بيعمل 3 حاجات مختلفة تمامًا: بيخزّن، وبيبعت إيميل، وبيعمل تقرير.

النتيجة
  • لو طريقة إرسال الإيميل اتغيّرت → نعدّل User.
  • لو شكل التقرير اتغيّر → نعدّل نفس الـclass.
  • لو اتحولنا من MySQL لـPostgres → نعدّل نفس الـclass.

تلات فرق مختلفة بيعدّلوا نفس الملف — يعني تلات مصادر خطر على نفس الكود.

2شكل أفضل

class UserRepository
{
    public function save(User $user): void
    {
        // save user
    }
}

class EmailService
{
    public function send(Email $email): void
    {
        // send email
    }
}

class ReportService
{
    public function generate(User $user): Report
    {
        // generate report
    }
}

والـUser نفسه بقى مسؤول عن بيانات وقواعد المستخدم بس — الاسم، الإيميل، الصلاحيات، تغيير الباسورد.

3إزاي أعرف؟

لو الإجابة «آه» على السؤال الذهبي لأن User هو اللي شايل مسؤولية الإيميل، غالبًا عندك مشكلة في SRP. افصل المسؤوليات بحيث كل جزء يتغيّر بسبب واحد.

اختبار الفريق

اسأل: مين في الشركة ممكن يطلب تغيير في الـclass دي؟ لو الإجابة «فريق المدفوعات، وفريق الماركتنج، وفريق البنية التحتية» — دي تلات مسؤوليات، مش واحدة.

4الحدود الصح

SRP مش «كل class تبقى صغيرة»

class فيها 10 methods كلهم بيخصوا قواعد الطلب = SRP سليمة. وclass فيها method واحدة بتعمل ثلاث حاجات = SRP مكسورة.

المعيار: التماسك (cohesion) — هل الحاجات اللي جوه الـclass بتتغيّر مع بعض؟ اقرا التفاصيل والأمثلة في صفحة SRP في قسم OOP.

Responsibility — مين مسؤول عن إيه؟

أهم سؤال تسأله وأنت بتصمم: العملية دي مين صاحبها الطبيعي؟ معظم مشاكل التصميم بتبدأ من object بيعمل شغل مش بتاعه.

افتكرها

لما تشوف عملية بتحصل، اسأل: «مين صاحب المسؤولية الطبيعية عن العملية دي؟»

1المشكلة

public function processPayment()
{
    // ...
    if ($this->paymentMethod === 'wallet') {
        if ($this->customer->walletBalance >= $total) {
            $this->customer->walletBalance -= $total;   // ← هنا
            $this->status = 'paid';
            return true;
        }
    }
}

السطر ده جوه Order. يعني الـOrder هو اللي:

  • بيقرأ رصيد الـWallet.
  • بيقارن الرصيد بالمبلغ.
  • بيخصم من الرصيد بنفسه.
السؤال المهم

هل الـOrder هو المسؤول عن قواعد الفلوس؟

الإجابة الأقرب: لأ. الـWallet هي اللي مسؤولة عن رصيدها.

2ليه دي مشكلة كبيرة؟

تخيّل بعد 6 شهور، بقى عندك 5 أماكن في المشروع بيخصموا من الـwallet:

Order → $wallet->balance -= $total RefundService → $wallet->balance += $amount AdminPanel → $wallet->balance = $newValue Subscription → $wallet->balance -= $monthly Migration → $wallet->balance -= $fee

دلوقتي جالك requirement جديد: «ممنوع الرصيد ينزل تحت الصفر، وكل حركة لازم تتسجل في transaction log.»

كام مكان هتعدّل؟ خمسة. وهتنسى واحد منهم على الأقل — وده مش تشاؤم، ده اللي بيحصل فعلًا.

لما المسؤولية تكون في مكانها
class Wallet
{
    private int $balanceInCents = 0;

    public function debit(Money $amount): void
    {
        if ($amount->isGreaterThan($this->balance())) {
            throw new InsufficientFunds();
        }

        $this->balanceInCents -= $amount->cents();
        $this->log(new WalletDebited($amount));
    }
}

دلوقتي القاعدة الجديدة اتكتبت في مكان واحد، وكل الـcallers استفادوا منها فورًا — من غير ما تلمسهم.

3إزاي تحدد صاحب المسؤولية؟

في 3 أسئلة عملية بتوصلك للإجابة في ثواني:

السؤالبيوصلك لإيه
مين بيملك البيانات اللي العملية دي محتاجة تعدّلها؟غالبًا هو ده صاحب العملية. الـbalance بتاع الـWallet → الـWallet.
مين لو اتغيّرت قواعده، العملية دي لازم تتغيّر؟لو قواعد الفلوس اتغيرت، مين المفروض يتأثر؟ الـWallet مش الـOrder.
لو حذفت الـclass دي، العملية دي تروح فين؟لو حذفت الـOrder، الـWallet لسه محتاجة تعرف تخصم. يبقى الخصم مش تبع الـOrder.

4الخريطة الطبيعية للمسؤوليات

Order → يعرف الـitems وقيمة الطلب وحالته Wallet → يعرف الرصيد وإزاي يخصم ويضيف PaymentGateway → يعرف إزاي ينفّذ الدفع فعليًا EmailSender → يعرف إزاي يبعت email OrderRepository→ يعرف إزاي يخزّن ويسترجع الطلب

لاحظ إن كل سطر بيبدأ بـ«يعرف». دي طريقة ممتازة تختبر بيها التصميم: لو الـclass بتعرف حاجة مش من طبيعتها، فهي شايلة مسؤولية مش بتاعتها.

5الفرق بين Responsibility و SRP

الاتنين قرايب لكن مش نفس الحاجة:

ResponsibilitySRP
السؤالالعملية دي بتخص مين؟الـclass دي شايلة كام شغلانة مختلفة؟
الاتجاهمن العملية → للـclassمن الـclass → للعمليات اللي جواها
المثالخصم الفلوس شغل الـWallet مش الـOrderالـOrder بيحسب ويدفع ويبعت email ويحفظ في ملف

عمليًا: بتستخدم Responsibility وأنت بتقرر العملية تتحط فين، وبتستخدم SRP وأنت بتراجع class موجودة وتشوف هي شايلة إيه. اقرا التفاصيل في صفحة SRP.

6Interview

سؤال شائع: ليه فصلت الخصم في الـWallet؟

«لأن الـWallet هي اللي بتملك الرصيد، فهي اللي المفروض تحمي قواعده — زي إن الرصيد ما ينزلش تحت الصفر أو إن كل حركة تتسجّل. لو سيبت كل class تخصم بنفسها، القاعدة دي هتتكرر في كل مكان، وأول ما تتغير هضطر أعدل في كذا مكان وأنسى واحد منهم.»

الخلاصة

كل object يبقى صاحب الحاجة اللي تخصه.

Tight & Loose Coupling

الـCoupling يعني: قد إيه component مرتبط بتفاصيل component تاني. وده أهم مقياس عملي لجودة التصميم.

افتكرها

Tight Coupling: الكلاسات لازقة في implementations معينة. Loose Coupling: الـclass عارف هو محتاج إيه، لكن مش مهتم الحاجة دي اتعملت إزاي.

1Coupling يعني إيه بالظبط؟

الـcoupling هو مقدار المعرفة اللي class محتاجة تعرفها عن class تانية عشان تشتغل. وكل ما المعرفة دي تزيد، كل ما التغيير يبقى أصعب.

class OrderService
{
    public function createOrder()
    {
        $gateway = new StripePaymentGateway();   // ← هنا
        $gateway->charge(100);
    }
}

الـOrderService هنا عارف:

  • إن فيه class اسمها StripePaymentGateway بالاسم.
  • إزاي يبنيها (بيعمل new بنفسه).
  • إن الـmethod اسمها charge بالشكل ده.
النتيجة

لو عايز PayPal بدل Stripe، هتدخل تعدّل OrderService — وهي أصلًا مالهاش علاقة ببوابات الدفع. ولو عايز تعمل test من غير ما تتصل بـStripe فعليًا، مش هتعرف.

2Loose Coupling

بدل ما أقول «هاتلي Stripe»، أقول: «أنا محتاج حاجة تعرف تنفّذ دفع».

interface PaymentGateway
{
    public function charge(Money $amount): PaymentResult;
}

class OrderService
{
    public function __construct(
        private PaymentGateway $gateway
    ) {}

    public function createOrder(): void
    {
        $this->gateway->charge($this->total);
    }
}

دلوقتي الـOrderService مش فارق معاه اللي قدامه:

PaymentGateway (contract) ↑ ├── StripeGateway ├── PayPalGateway ├── FawryGateway └── FakeGateway ← للـtesting

طالما بيحقق الـcontract المطلوب، الـOrderService هيشتغل معاه من غير أي تعديل.

3درجات الـCoupling — من الأسوأ للأحسن

قاعدة عملية بسيطة: «اتكلم مع أصحابك، مش مع أصحاب أصحابك.»

✕ سلسلة طويلة (خطر)
$order->customer()->wallet()->balance()->subtract(50);
✓ خطوة واحدة
$order->payFrom($wallet);

كل نقطة زيادة في السلسلة = معرفة زيادة عن البنية الداخلية = مكان زيادة ممكن يتكسر لما البنية تتغير.

4الغلطة الشائعة: صفر coupling

الهدف مش تشيل الـcoupling خالص

مستحيل يبقى عندك نظام أجزاؤه مش مرتبطة ببعض — لو كده مش هيبقى نظام أصلًا. الهدف الحقيقي:

  • الارتباط يكون على الـcontract الثابت مش على التفاصيل المتغيرة.
  • الارتباط يكون في اتجاه واحد، مش دايري (A تعرف B وB تعرف A).
  • الارتباط يكون واضح ومعلن في الـconstructor، مش مخفي جوه method.

لو عملت interface لكل حاجة في المشروع «عشان loose coupling»، هتلاقي نفسك بتفتح 4 ملفات عشان تفهم سطر واحد. الـinterface يستحق لما يكون فيه احتمال حقيقي لأكتر من implementation، أو محتاجه للـtesting.

5إزاي تقيس الـcoupling عمليًا؟

3 أسئلة سريعة على أي class:

  1. لو غيّرت مزوّد خارجي، كام ملف هفتح؟ واحد = ممتاز. عشرة = tight coupling.
  2. أقدر أعمل unit test للـclass دي من غير database أو network؟ لو لأ، فهي لازقة في التفاصيل.
  3. أقدر أشرح الـclass دي لوحدها من غير ما أشرح 3 classes تانية؟ لو لأ، فالـcoupling عالي.

6Interview

سؤال: إزاي تقلل الـcoupling؟

«بخلي الـclass تعتمد على interface بدل implementation، والـdependency تيجي لها من بره بدل ما تعملها new بنفسها. كده الـclass بتعرف إنها محتاجة إيه، لكن مش عارفة مين اللي هينفذه، وبالتالي أقدر أبدّل المزوّد أو أحقن fake في الـtests من غير ما ألمس الـbusiness logic.»

Follow-up متوقع: «هل نعمل interface لكل class؟» — لأ. الـinterface تستحق لما يكون فيه احتمال حقيقي لأكتر من implementation أو محتاجه للـtesting. غير كده بتضيف طبقة بدون قيمة.

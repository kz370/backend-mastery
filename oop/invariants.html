Invariants — قواعد لازم تفضل صح

الـobject لازم يحافظ على قواعده الأساسية، ومينفعش أي caller يدخل data تكسر القواعد دي — حتى بالغلط.

افتكرها

Invariant = rule لازم تفضل صحيحة جوه الـobject طول عمره، من لحظة إنشائه لآخر لحظة.

1المشكلة

$order->addItem($mouse, -5);        // كمية بالسالب؟
$order->applyDiscount('HELLO');     // كوبون مش موجود — بيعدّي في صمت
$order->addItem($keyboard, 0);      // صفر قطعة؟

تعالى نبص على applyDiscount في المشروع:

public function applyDiscount($code)
{
    if ($code === 'SAVE10') {
        $this->discountPercent = 10;
    } elseif ($code === 'SAVE25') {
        $this->discountPercent = 25;
    }
    // مفيش else — الكوبون الغلط بيعدّي من غير أي رد فعل
}
الفشل الصامت

العميل كتب كوبون غلط، والنظام قبله من غير ما يقول حاجة، وخلّص الطلب من غير خصم.

العميل هيفتكر إن الخصم اتطبّق، وخدمة العملاء هتقعد تدوّر في اللوجز، والـdeveloper هيقول «الكود شغال صح» — لأنه فعلًا مرمّاش error.

الفشل الصامت أخطر من الـexception، لأن الـexception بيوقّفك عند المشكلة، والصمت بيسيبها تكبر.

2فين تتحط القاعدة؟

الغلطة الشائعة إن الـvalidation تتحط في الـController بس:

Controller → validate → Order ✓ الطريق ده محمي Console cmd → → Order ✗ مش محمي Job/Queue → → Order ✗ مش محمي Seeder → → Order ✗ مش محمي Test → → Order ✗ مش محمي

القاعدة اللي في الـController بتحمي طريق واحد بس. القاعدة اللي جوه الـOrder بتحمي كل الطرق.

class Order
{
    public function addItem(Product $product, int $quantity): void
    {
        if ($quantity < 1) {
            throw new InvalidArgumentException(
                'Quantity must be at least 1.'
            );
        }

        if ($this->status !== OrderStatus::Pending) {
            throw new DomainException(
                'Cannot add items to a non-pending order.'
            );
        }

        $this->items[] = new OrderItem($product, $quantity);
    }
}
طبقتين مش واحدة

الـvalidation في الـController وظيفتها تجربة مستخدم كويسة (رسالة واضحة قبل ما يبعت). الـinvariant جوه الـobject وظيفتها ضمان صحة الـdomain. الاتنين مطلوبين، وكل واحدة لها سبب مختلف — فوجودهم مع بعض مش تكرار.

3أقوى شكل: الـobject ما يتعملش غلط أصلًا

أفضل من إنك تتحقق بعد الإنشاء إنك تمنع الإنشاء الغلط من الأساس:

✕ تحقق متأخر
$item = new OrderItem();
$item->quantity = -5;
$item->validate();   // ممكن حد ينسى ينادي دي
✓ مستحيل يتعمل غلط
final class Quantity
{
    private function __construct(
        public readonly int $value
    ) {}

    public static function of(int $value): self
    {
        if ($value < 1) {
            throw new InvalidArgumentException(
                'Quantity must be at least 1.'
            );
        }

        return new self($value);
    }
}

دلوقتي أي كود في المشروع بيتعامل مع Quantity ضامن إنها موجبة — من غير ما يتحقق. النوع نفسه بقى دليل على الصحة.

ده اسمه «make illegal states unrepresentable» — بدل ما تحرس على الحالة الغلط، تمنع وجودها أصلًا.

4أنواع الـInvariants

النوعالمثال
على قيمةquantity >= 1 · email شكله صح
على علاقةالطلب لازم يكون له customer · مفيش item بمنتج محذوف
على حالةمينفعش تضيف items لطلب اتشحن
على انتقالpending → paid مسموح، shipped → pending ممنوع
مجمّعةمجموع خصومات الطلب ما يتعداش 50% من الإجمالي

5Exception ولا قيمة راجعة؟

الحالةالأنسب
خطأ برمجي (مفروض ما يحصلش)throw — زي quantity بالسالب من كود داخلي
إدخال متوقع من مستخدمResult أو رسالة validation — زي كوبون منتهي
حالة نادرة لكن ممكنةthrow بexception مسمّى (InsufficientFunds)

المهم: أيًّا كان اختيارك، لازم يكون فيه رد فعل واضح. اللي ممنوع تمامًا هو الصمت.

6Interview

سؤال: فين تحط الـvalidation؟

«في مستويين: في الـrequest عشان أدّي المستخدم رسالة واضحة بدري، وجوه الـdomain object عشان أضمن إن القاعدة محفوظة مهما كان مصدر النداء — controller، job، console command، أو seeder. الأولى تجربة استخدام، والتانية سلامة الـdomain. ولو أقدر أستخدم value object يمنع القيمة الغلط من الأصل، ده أحسن من الاتنين لأن النوع نفسه بيبقى ضمان.»

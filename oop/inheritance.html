Inheritance — استخدمه لما العلاقة تكون is-a

مش كل behavior مختلف معناه لازم أعمل subclass. الوراثة أقوى ارتباط ممكن بين كلاسين — فلازم تستحقه.

افتكرها

استخدم الوراثة لما العلاقة فعلًا «ده نوع من ده»، مش لمجرد إن عندي behavior مختلف أو كود عايز أعيد استخدامه.

1مثال من المشروع

class VipOrder extends Order
{
    public function calculateTotal()
    {
        $total = 0;
        foreach ($this->items as $item) {
            $total += $item['product']->price * $item['quantity'];
        }
        return $total * 0.8;   // VIP دايمًا بيدفع أقل 20%
    }
}

جرّب التجربة دي بنفسك قبل ما تكمل قراءة:

التجربة
$order = new VipOrder($khaled);
$order->addItem($keyboard, 1);      // 100
$order->applyDiscount('SAVE10');    // 10%
$order->paymentMethod = 'creditcard';
$order->processPayment();

احسب المبلغ المتوقع قبل ما تشغّل، وبعدين شغّل وقارن. النتيجة هتفاجئك.

السبب: calculateTotal() في الابن بترجّع 80، وبعدين processPayment() بتطبّق الـ10% على الـ80. يعني الخصمين اتراكموا — وده مش المقصود، ومحدش كان واخد باله.

2السؤال التصميمي الحقيقي

هل الـVIP فعلًا نوع مختلف من الطلب؟

Order = الطلب نفسه Customer = العميل VIP = صفة للعميل، مش نوع للطلب

الطلب هو الطلب — items وسعر وحالة. اللي بيتغيّر هو قواعد التسعير المطبّقة عليه، وسببها صفة في العميل مش نوع في الطلب.

تخيّل الأسئلة دي:

  • لو العميل بقى VIP بعد ما عمل الطلب، الطلب القديم يتحوّل لـVipOrder؟
  • لو العميل خرج من الـVIP، إيه اللي يحصل للطلبات الجاية؟
  • لو بقى فيه StudentOrder وEmployeeOrder كمان، تعمل VipStudentOrder؟

الأسئلة دي كلها بتبقى صعبة مع الوراثة، وبديهية مع الـcomposition.

3الحل الأنضف

class Customer
{
    public function __construct(
        private CustomerTier $tier = CustomerTier::Regular
    ) {}

    public function tier(): CustomerTier
    {
        return $this->tier;
    }
}

class Order
{
    public function total(): Money
    {
        $subtotal = $this->subtotal();
        $subtotal = $this->customer->tier()->applyTo($subtotal);

        return $this->coupon
            ? $this->coupon->applyTo($subtotal)
            : $subtotal;
    }
}

دلوقتي:

  • فيه Order واحد بس.
  • ترتيب تطبيق الخصومات واضح ومكتوب في مكان واحد.
  • ترقية العميل لـVIP سطر واحد — مش تحويل نوع object.
  • إضافة tier جديد ما تحتاجش class طلب جديدة.

4اختبار العلاقة قبل ما تورّث

قبل ما تكتب extends، جاوب على التلاتة دول:

  1. is-a صح؟ «كل VipOrder هو Order» — الجملة دي صحيحة لغويًا لكن مش صحيحة في الـdomain، لأن الـVIP صفة للعميل.
  2. Liskov؟ هل أقدر أستخدم الابن مكان الأب في أي مكان من غير مفاجآت؟ (LSP)
  3. هيتغيّروا مع بعض؟ الوراثة بتربط الابن بتفاصيل الأب الداخلية — أي تعديل في الأب ممكن يكسر الأبناء.
المشكلة اللي محدش بيتكلم عنها

الوراثة بتربط الابن مش بس بـواجهة الأب، لكن بـتفاصيله الداخلية كمان. لو الأب غيّر إنه بينادي method داخلية بدل التانية، ممكن الابن يتكسر — وده اسمه fragile base class problem.

عشان كده القاعدة الشهيرة: «Favor composition over inheritance». مش لأن الوراثة وحشة، لكن لأنها أقوى ارتباط ممكن بين كلاسين، فسعرها عالي.

5امتى الوراثة تكون الاختيار الصح؟

الحالةمثال
علاقة نوع حقيقية ثابتةPdfReport extends Report — الـPDF فعلًا نوع من التقارير
Template Methodالأب فيه الـworkflow والابن بيملّي خطوة
توسيع frameworkclass UserController extends Controller

والعامل المشترك بينهم كلهم: النوع ثابت ومش بيتغيّر في وقت التشغيل. الـobject مش بيتحول من نوع لنوع.

6Composition — البديل

✕ Inheritance
class VipOrder extends Order
{
    // بيرث كل حاجة، حتى اللي مش محتاجها
    // ومربوط بتفاصيل الأب الداخلية
}
✓ Composition
class Order
{
    public function __construct(
        private PricingPolicy $pricing
    ) {}
    // بيستخدم اللي محتاجه بس
    // والـpolicy ممكن تتغير في وقت التشغيل
}

مع الـcomposition تقدر تغيّر السلوك في وقت التشغيل، وتركّب أكتر من سلوك مع بعض، وتختبر كل جزء لوحده. مع الوراثة، النوع بيتحدد وقت الإنشاء وخلاص.

7Interview

سؤال: امتى تستخدم inheritance وامتى composition؟

«بستخدم الوراثة لما تكون فيه علاقة نوع حقيقية وثابتة وكود مشترك فعلي — وأتأكد إن الابن ينفع مكان الأب من غير مفاجآت. غير كده بفضّل الـcomposition، لأن الوراثة بتربط الابن بتفاصيل الأب الداخلية وأي تعديل في الأب ممكن يكسر الأبناء. في مثال الـVipOrder مثلًا، الـVIP مش نوع من الطلب — دي صفة للعميل، فالأنسب إن الـOrder ياخد pricing policy بدل ما يبقى فيه نوعين طلب.»

الخلاصة

الوراثة أقوى ارتباط بين كلاسين. استخدمها لما العلاقة تستاهل السعر ده.

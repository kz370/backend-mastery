SRP — Single Responsibility Principle

الـclass مايبقاش ماسك مجموعة شغلانات مختلفة ملزوقة في بعض. لكن خد بالك: SRP مش معناها «كل class لازم تبقى صغيرة».

افتكرها

ما تحطش شغلانات ملهاش علاقة ببعض في نفس الـclass. المعيار مش عدد السطور — المعيار سبب التغيير.

1المشكلة

خد processPayment() من المشروع وعدّ العمليات اللي بتحصل جواها:

processPayment() 1. Calculate total ← حساب 2. Apply discount ← قواعد تسعير 3. Choose payment method ← اختيار 4. Execute payment ← تكامل مع بوابة دفع 5. Change wallet balance ← فلوس 6. Change order status ← دورة حياة الطلب

وبعدين في نفس الـclass كمان:

sendConfirmationEmail() ← إرسال بريد saveToFile() ← تخزين
سؤال بسيط

الـclass اسمها Order. هل كل ده فعلًا شغل الـOrder؟

2الاختبار الحقيقي: أسباب التغيير

النسخة الأدق للـSRP هي:

«الـclass يكون ليها سبب واحد للتغيير» — A class should have only one reason to change.

طب إزاي تختبرها عمليًا؟ اكتب قائمة الأسباب اللي ممكن تخليك تفتح الـOrder.php:

السببالجهة اللي طلبتهعلاقته بالـOrder؟
غيّرنا بوابة الدفع من Stripe لـPayPalفريق المدفوعات❌ مش شغله
الإيميل بقى بتصميم جديدفريق الماركتنج❌ مش شغله
بقينا نحفظ في database بدل ملففريق الـinfra❌ مش شغله
الكوبونات بقى ليها تاريخ انتهاءفريق المبيعات✅ ده شغله
أضفنا حالة جديدة: refundedفريق العمليات✅ ده شغله

خمس أسباب مختلفة، من خمس جهات مختلفة، بيفتحوا نفس الملف. ده معناه إن أي تعديل في أي واحد فيهم بيعرّض الباقي للخطر.

3التقسيم

Order → الـitems، الإجمالي، الخصم، الحالة PaymentGateway → تنفيذ الدفع Wallet → الرصيد، debit / credit Mailer → إرسال الإيميل OrderRepository → الحفظ والاسترجاع
class CheckoutService
{
    public function __construct(
        private PaymentGateway   $gateway,
        private Mailer           $mailer,
        private OrderRepository  $orders,
    ) {}

    public function checkout(Order $order): void
    {
        $this->gateway->charge($order->total());
        $order->markAsPaid();

        $this->orders->save($order);
        $this->mailer->send(new OrderConfirmation($order));
    }
}

دلوقتي الـOrder بقى مسؤول عن قواعد الطلب بس، والـCheckoutService مسؤول عن ترتيب الخطوات. وكل حتة تانية عندها شغلانتها.

4أهم سوء فهم في SRP

SRP مش معناها «كل class لازم تبقى صغيرة»

ناس كتير بتقرا SRP وتفهم منها إن الـclass المفروض تبقى فيها method واحدة أو اتنين. ده غلط، وبيوصل لتصميم أسوأ من الأصلي:

// over-engineering باسم SRP
class OrderTotalCalculator {}
class OrderDiscountApplier {}
class OrderItemAdder {}
class OrderItemRemover {}
class OrderStatusChanger {}
class OrderItemCounter {}

دلوقتي عشان تفهم إيه اللي بيحصل للطلب لازم تفتح 6 ملفات، والـOrder رجع صندوق بيانات تاني — يعني كسرت الـEncapsulation عشان تطبّق SRP.

الصح: الـOrder يبقى فيه كل الـmethods اللي بتخص قواعد الطلب — addItem, applyCoupon, total, markAsPaid — لأنهم كلهم بيتغيّروا لنفس السبب.

افتكرها

SRP مش عن الحجم، هي عن التماسك (cohesion). class كبيرة كل حاجة فيها بتتغير لنفس السبب أحسن من 6 classes صغيرة مبعثرة.

5علامات إن الـclass كسرت SRP

  • اسمها فيه «و» ضمنيًا: UserManager اللي بيسجّل ويبعت إيميل ويعمل تقارير.
  • الـimports في أولها من عوالم مختلفة: PDO + SmtpClient + PdfWriter.
  • لما تيجي تكتب unit test، بتحتاج تعمل mock لـ4 حاجات مالهاش علاقة ببعض.
  • developers من فرق مختلفة بيعدلوا نفس الملف كل أسبوع (شوف الـgit history — ده مؤشر قوي جدًا).
  • الاسم مبهم: Helper, Manager, Utils, Processor.
حيلة الـgit

جرّب git log --format=%s -- app/Order.php. لو الـcommit messages بتتكلم عن مواضيع مختلفة تمامًا (payments، emails، reports)، فالملف ده شايل أكتر من مسؤولية — والـgit بيقولك ده من غير ما تقرا الكود.

6Interview

لو سألك: What is SRP?

«إن الـclass يكون ليها سبب واحد أساسي للتغيير. يعني لو غيّرت طريقة إرسال الإيميل، ما ينفعش أضطر أفتح كلاس الـOrder. المعيار مش حجم الـclass ولا عدد الـmethods، المعيار إن الحاجات اللي جواها بتتغيّر مع بعض ولنفس السبب.»

Follow-up: «طب مش ده معناه classes كتير صغيرة؟» — الرد: لأ، التقسيم الزيادة بيكسر الـcohesion ويخلي فهم العملية محتاج فتح ملفات كتير. الهدف تماسك، مش تفتيت.

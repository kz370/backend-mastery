Encapsulation — التغليف

مش أي كود بره الـclass يكون مسموح له يغيّر البيانات الداخلية براحته. الـobject هو اللي يحمي حالته، والتغيير يحصل من خلال الـbehavior المناسب.

افتكرها

الـEncapsulation مش «خلي كل حاجة private». هو «الـobject هو الوحيد اللي يقدر يغيّر حالته، وبقواعده هو».

1المشكلة

تعالى نبص على الكود ده من المشروع العملي:

class Order
{
    public $items = [];
    public $customer;
    public $status = 'pending';
    public $discountPercent = 0;
}

// وفي أي مكان تاني في المشروع:
$order->status = 'shipped';
$order->discountPercent = 90;
$order->items = [];
إيه اللي غلط هنا؟

مفيش حاجة بتمنع أي كود في المشروع إنه:

  • يخلي الـstatus = 'shipped' والطلب أصلًا لسه ما اتدفعش.
  • يحط خصم 90% من غير كوبون.
  • يفضّي الـitems بعد ما الطلب اتدفع.
  • يحط status = 'bananas' — والكود هيقبلها عادي.

النتيجة: الـOrder بقى مجرد صندوق بيانات، مش object له قواعد. ولما تظهر مشكلة في الـproduction، هتدور في المشروع كله على مين غيّر الـstatus.

2ليه دي مشكلة فعلًا؟

خد بالك من نقطة مهمة كتير الناس بتفوّتها: المشكلة مش «الـproperty عامة». المشكلة إن القاعدة اللي بتحكم التغيير مش موجودة في مكان واحد.

public property ↓ كل كود يقدر يغيّر ↓ القاعدة اتكررت في كل مكان (أو اتنسيت) ↓ حالات مستحيلة (impossible states) تظهر في الـDB

لما تخلي التغيير يعدّي من method واحدة، بتكسب 3 حاجات:

  1. مكان واحد للقاعدة — لو القاعدة اتغيّرت، تعدل في مكان واحد.
  2. مكان واحد تحط فيه breakpoint — لما تدوّر على bug، عارف تروح فين.
  3. الـstate دايمًا صالح — مستحيل يبقى عندك order مدفوع بـitems فاضية.

3الحل

✕ state مكشوف
class Order
{
    public $status = 'pending';
}

$order->status = 'paid';
$order->status = 'shipped';
$order->status = 'anything';
✓ state محمي بسلوك
class Order
{
    private string $status = 'pending';

    public function markAsPaid(): void
    {
        if ($this->status !== 'pending') {
            throw new DomainException(
                'Only a pending order can be paid.'
            );
        }

        $this->status = 'paid';
    }

    public function status(): string
    {
        return $this->status;
    }
}

بص على الفرق: دلوقتي جملة $order->markAsPaid() بتحمل معنى في الـdomain. أما $order->status = 'paid' فهي مجرد تعديل حرف في متغير.

4الغلطة الشائعة: getters و setters لكل حاجة

ده مش encapsulation
class Order
{
    private $status;

    public function getStatus() { return $this->status; }
    public function setStatus($s) { $this->status = $s; }
}

لو كل private عندها set عامة بتغيرها من غير أي شرط، فأنت عملت نفس الـpublic property بس بخطوتين. الـsetStatus() دي مجرد باب خلفي.

السؤال الصح: «إيه العمليات اللي ممكن تحصل للـOrder؟» مش «إيه الـproperties اللي ممكن أعدلها؟»

بدل ما تكتباكتب
setStatus('paid')markAsPaid()
setStatus('shipped')ship()
setDiscount(10)applyCoupon('SAVE10')
setBalance($b - 50)debit(50)

لاحظ إن كل واحدة على اليمين بتوصف عملية في الـdomain، وبالتالي فيها مكان طبيعي تحط فيه القواعد.

5إمتى الـpublic مقبول؟

مش كل حاجة لازم تتقفل. الـpublic مقبول لما:

  • الـobject أصلًا Value Object ثابت (immutable) — زي Money أو Email، اتبنى صح مرة واحدة ومحدش بيغيره بعد كده.
  • الـclass عبارة عن DTO بينقل بيانات بين طبقتين ومفيهاش قواعد أصلًا.
  • الـproperty فعلًا ملهاش قاعدة، وتغييرها من بره مش هيخلي الـobject في حالة غلط.
قاعدة عملية

اسأل: «لو حد من بره غيّر الـproperty دي لأي قيمة، هل ممكن الـobject يبقى في حالة مستحيلة؟» لو الإجابة آه → اقفلها وحط behavior.

6في المشروع بتاعنا

لو رجعنا لمشروع الـOrder، الحاجات اللي المفروض تتقفل:

الـPropertyليه؟
statusله دورة حياة: pending → paid → shipped. مش أي قيمة تنفع في أي وقت.
itemsإضافة item ليها قواعد (quantity > 0). والإضافة بعد الدفع مش منطقية.
discountPercentمالوش معنى لوحده — هو نتيجة كوبون صالح، مش رقم عشوائي.
customerالطلب بيتعمل لعميل واحد. تغييره بعد الإنشاء يكسر معنى الطلب.
walletBalanceدي أخطر واحدة — فلوس. مفيش كود بره الـWallet يعدّلها مباشرة.

7Interview

لو سألك: What is Encapsulation?

«الـEncapsulation إن الـobject يحمي الـstate بتاعه، فمش أي كود من بره يقدر يعدّله مباشرة. التغيير بيحصل من خلال methods بتمثل عمليات حقيقية في الـdomain، وفيها القواعد. الهدف مش إخفاء البيانات في حد ذاته، الهدف إن الـobject يفضل دايمًا في حالة صالحة.»

Follow-up متوقع: «طب مش getters و setters بيعملوا كده؟» — الرد: لأ، الـsetter اللي بيحط أي قيمة من غير شرط بيرجّعك لنفس مشكلة الـpublic property، بس بشكل أطول.

الخلاصة

احمي الـstate، وخلّي التغيير يحصل من خلال الـbehavior المناسب.

Dependency Injection

الحاجة اللي الـclass محتاجها تيجي له من بره، بدل ما يعملها new بنفسه. لكن الفكرة أعمق من مجرد نقل الـnew للـconstructor.

افتكرها

DI مش مجرد إنك تحط dependency في الـconstructor. الفكرة: الـclass ما ينشئش dependencies بنفسه؛ إنشاؤها يبقى خارج الـbusiness logic.

1المشكلة

class Order
{
    public function sendConfirmationEmail(): void
    {
        $emailSender = new EmailSender();      // ← هنا
        $emailSender->send($this->customer->email, 'Order confirmation', $body);
    }
}

الـOrder بقى:

  1. عارف dependency معينة بالاسم.
  2. مسؤول عن إنشائها وعن الـconfig بتاعها.
  3. مربوط بيها، فصعب تبدّلها في الـtesting أو في المستقبل.
التأثير على الـtesting

لو عايز تعمل test للـOrder، كل مرة هيتبعت إيميل حقيقي. مفيش طريقة تمنعه غير:

  • إنك تشغّل SMTP server وهمي (بطيء ومعقّد)، أو
  • تحط if ($env === 'testing') جوه الـbusiness logic (كارثة)، أو
  • ما تعملش test أصلًا (اللي بيحصل غالبًا).

2قلب الاتجاه

✕ الـclass بينشئ dependencies
Order ↓ new EmailSender() ↓ SMTP config
✓ الـdependency بتيجي من بره
Container / Caller ↓ بينشئ Mailer ↓ بيحقن Order
class Order
{
    public function __construct(
        private Mailer $mailer
    ) {}

    public function sendConfirmation(): void
    {
        $this->mailer->send(new OrderConfirmation($this));
    }
}

// في الـproduction
$order = new Order(new SmtpMailer($config));

// في الـtest
$order = new Order(new FakeMailer());

قاعدة

لو الـobject مينفعش يشتغل من غير الـdependency → constructor. كده مستحيل يتعمل object في حالة ناقصة.

4DI مش DI Container

أشهر خلط

Dependency Injection = فكرة تصميم: الـdependencies تيجي من بره.

DI Container = أداة (زي الـservice container في Laravel) بتأتمت إنشاء الـobjects دي.

تقدر تعمل DI صح من غير أي container خالص — بإنك تبني الـobjects بإيدك في نقطة واحدة. والعكس صحيح: ممكن تستخدم container وتفضل تكسر الـDI:

class Order
{
    public function send(): void
    {
        // الـcontainer موجود، لكن الـclass لسه بتجيب dependency بنفسها
        $mailer = app(Mailer::class);      // Service Locator، مش DI
        $mailer->send(...);
    }
}

ده اسمه Service Locator. الفرق الجوهري: مع الـDI، الـdependencies بتاعة الـclass معلنة في الـconstructor وأي حد يبص على الـsignature يعرفها. مع الـService Locator، مخبّية جوه الـmethods ومحدش يعرفها غير لما يقرا كل سطر.

5الغلطات الشائعة

  • Constructor بـ12 dependency — ده مش مشكلة DI، ده الـclass كسرت SRP. الـDI بس فضحتها.
  • حقن الـContainer نفسه — __construct(Container $c) بيرجّعك لـService Locator.
  • حقن قيم configuration كـobjects — الـAPI key مش dependency، مرّرها كـvalue.
  • عمل interface لكل حاجة عشان تحقنها — الحقن ممكن يحصل على class عادية برضه.
الـconstructor كمقياس جودة

عدد الـdependencies في الـconstructor مؤشر مجاني على الـSRP. تلاتة أو أربعة = طبيعي. تمانية = الـclass بتعمل شغل أكتر من اللازم — مش المطلوب تخبّي الحقن، المطلوب تقسّم الـclass.

6Interview

سؤال: ليه DI مهمة؟

«عشان الـclass تركّز على شغلها بس، ومسؤولية إنشاء وتوصيل الـdependencies تبقى برّه. ده بيديني تلات مكاسب: أقدر أبدّل الـimplementation من غير ما ألمس الـbusiness logic، أقدر أحقن fake في الـtests، والـclass بتعلن احتياجاتها بوضوح في الـconstructor فأي حد يقراها يعرف هي معتمدة على إيه.»

Follow-up: «الفرق بين DI و DI Container؟» — الأولى فكرة تصميم، والتانية أداة بتأتمت التوصيل. تقدر تعمل DI من غير container، وتقدر تستخدم container وتكسر الـDI بالـService Locator.
